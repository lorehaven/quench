# Quench Android Surface

`quench-android-surface` (crate `quench_android_surface`) is the program side of an **Android app drawn by the native renderer**: no WebView. The Kotlin host (the `surface` plugin: `quench plugin add surface`) owns a `SurfaceView`, the input method and the accessibility services, and starts this program as a **process of its own** (no JNI, no `unsafe`, as for the `native` plugin). The two talk over the program's standard input and output.

```rust
let renderer = Rc::new(NativeRenderer::new());
// stylesheets, mount(&renderer, &renderer.root(), view)
quench_android_surface::run(&renderer)?;
```

**The protocol** (`proto`): a length, a kind and a payload, numbers big-endian (what Java's `DataInputStream` reads). Host to program: resize (pixels, density, system-bar insets), a touch (down, move, up, cancel), a key (DOM `key` name and modifiers), committed text, a composition (cursor in UTF-16 units), delete around the caret, an accessibility action, the colour scheme, back, visibility, the system clipboard's text, a plugin's answer or event. Program to host: a frame (RGBA, premultiplied: the byte order of an Android bitmap), text for the system clipboard, a call to a plugin, show or hide the keyboard, the focused field (text, caret, selection and the caret's rectangle), the **accessibility tree** flattened (`encode_tree`: id, parent, role, flags, level, bounds, name, value, description), back handled, exit.

**The clipboard**: Ctrl+C or Ctrl+X in the program sends the text (`Out::Clipboard`) and the host puts it on the `ClipboardManager`; the host sends the system's text (`Event::Clipboard`) when the clip changes and when the app comes back to the front (not what the program itself just put there), and a Ctrl+V pastes it. Text only.

**Calling the host's plugins** (`Bridge`): the activity gives the program the same plugins a web page gets (`device`, `files`, `notifications`, `packages`, your own; whatever `plugins()` in `Plugins.kt` lists), through the same Kotlin `Bridge` (it has a `sink` instead of a page's `MessagePort`). The program makes one `Bridge`, passes it to `run_with(&renderer, &bridge)` and calls from any view: `bridge.call("device", "state", Value::Null, |answer| ...)`; the closure gets the plugin's JSON answer or a `CallError { code, message }` (`unknown_plugin`, `invalid_args`, `permission_denied`...). `bridge.on(plugin, event, |data| ...)` receives the events a plugin pushes. Both ride the protocol as JSON envelopes, the page's own (`{"id","plugin","method","args"}` out, `{"id","ok"}`, `{"id","err"}` or `{"event","plugin","data"}` back), so a plugin needs no change; the activity forwards permission results, activity results and new intents to the plugins as `MainActivity` does. The template's app has an "Ask the host" button that calls `echo.device`.

**What the program does with it** (`Surface`): the density becomes the renderer's scale (a CSS pixel is 2.625 device pixels on a Pixel 8; `@media` sees CSS pixels; the insets reach the page as `env(safe-area-inset-*)`); a **tap** is a click, a finger that moves past 8 CSS pixels **scrolls what is under it** and clicks nothing (and a finger leaves no `:hover` behind); the media say `hover: none`, `pointer: coarse`; keys and the input method edit the focused field in the renderer; the soft keyboard is requested when a text field gets focus and dismissed when it loses it; **Back** is sent to the page as Escape and, when no listener took it, the program tells the host to leave; frames are sent only when something changed and not while the app is in the background; the tree is sent when it changed.

**Fling**: a drag that leaves the screen faster than 150 device pixels a second keeps the content moving at that speed, slowing down (a factor of `e^-3.5` a second) until it is slower than 25 pixels a second; a finger on the page stops it. It runs on the program's timers (a step every 16 ms), so nothing is sent while the page is still.

**Selecting text**: a finger that stays put for half a second on a text field selects the word under it (`select_word_at`), and a handle appears at each end of the selection (a stem along the caret and a knob below it, drawn by the program into the frame); a finger that comes down on a knob drags that end (`move_selection_end`), and may cross the other. A selection press is not a click. There is no floating menu: copy, cut and paste go through the hardware keyboard's Ctrl+C, X and V and the system clipboard.

**Accessibility ranges**: the tree carries, for a slider or progress bar, its smallest, largest and current value (NaN while indeterminate), which the host gives TalkBack as `RangeInfo`. **The program's home**: the host starts the program with the app's files directory as its working directory and `HOME`, so what it keeps (a session, a database) is in the app's own storage.

**The launcher**: `quench android launcher surface` makes `.SurfaceActivity` the activity the home screen starts (the intent filter moves out of `.MainActivity`); `quench android launcher web` puts it back.

**The Kotlin side** (`SurfaceHost`, `QuenchSurfaceView`, `SurfaceActivity`, in `quench-tool/templates/android/plugins/surface`): frames are drawn with `lockCanvas`; touches and hardware keys are forwarded; an `InputConnection` forwards `commitText`, `setComposingText`, `deleteSurroundingText` and answers the keyboard's questions from the last field state; an `AccessibilityNodeProvider` builds `AccessibilityNodeInfo`s (class by role, text, hint, bounds, checked, clickable, focusable, heading, the click, focus and show-on-screen actions) from the program's tree and sends clicks back. `quench android build-native` builds `{name}-surface` (as `libquench_surface.so`) beside `{name}-native` when the project has them. The activity is exported (`am start -n <package>/.SurfaceActivity`); to make it the launcher, move the `LAUNCHER` intent filter to it.

**Verified** on the Pixel 8 emulator by `scripts/android-surface-e2e.fish` (a new project, the plugin, the NDK build, Gradle, install, launch): the program runs as its own process; the accessibility tree read back through `uiautomator` (the same node tree TalkBack reads) has the page with the right classes (`Button`, `EditText`, `CheckBox`), texts and bounds; two real taps press the button twice; a plugin of the host answers a call made by the program (`echo.device`, through the bridge); text typed with `adb shell input text` reaches the field; a tap checks the box; the soft keyboard comes up and goes away with the field's focus (seen in the insets). **Not verified:** the clipboard on a device (the protocol and the program's side are unit-tested; the `ClipboardManager` code is not run), TalkBack itself, composition through a real input method (`input text` sends key events; the `InputConnection` and the program's handling of composition and deletion are unit-tested on the program side only), a physical device, a release build, the feel of a fling and of the long press on a real finger (their rules are unit-tested), and the selection handles on a device.
